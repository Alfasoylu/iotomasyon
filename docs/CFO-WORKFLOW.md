# Persistent CFO working loop — 2026-10-04

Implemented on the existing application/database connection without migrations or new provider credentials. Owner-facing `/cfo/calisan` reads durable research items, questions, approval status, reported outcomes and a success heartbeat. Existing CFO questions and notebook remain the persistent memory. No private business records, original uploads or notebook text are fixtures or documentation.

## Working behavior

- The existing daily XML (02:00 UTC) and Trendyol (06:00 UTC) cron jobs run the CFO after their response, even if their source is disabled or empty. Both use the existing fail-closed CRON_SECRET gate. No additional Hobby cron job slot is required. Successful bank/Entegra uploads, balance updates, XML/Trendyol syncs and question answers additionally schedule evaluation with Next.js `after`. A manual ADMIN/CFO_WRITE action runs the same loop. After-response execution is best effort within the platform duration; daily cron retries missed events. This is daily plus event-driven operation, not a continuously resident or hourly worker. Upgrading to Pro is not required for this release.
- Each cycle loads the reviewed financial sources, existing costs, stock/receivables, active notebook, settings and previous questions. It uses an advisory transaction lock across observation and persistence; concurrent cycles return `already_running`. Preview deployments cannot write workflow records.
- Unique Unicode/case SKU aliases preserve digits and punctuation; exact matches win and ambiguous aliases fail closed. Financial cost and SQL weight lookups use the same uniqueness rule. Raw identifiers and business tables are not rewritten. Channel ingestion freshness, actual canonical financial-source freshness and XML inventory freshness are separate. A fresh native channel does not make stale canonical financial observations current.
- Explicit no-reorder language in Product.privateNote restricts procurement, separately from catalog activity and liquidation. Listing packages and verified dummy stock do not become stock-based procurement candidates. Missing cost does not mean unwanted stock. Case variants of notebook confidence tags are accepted; custom confidence tags remain unverified.
- The deterministic planner detects critical stock cover, excess stock, below-floor observed pricing when the canonical financial source is current, cash-floor risk and growth measurement gaps. It creates research items with evidence, blockers and nullable financial impacts. Stock quantities are explicitly illustrative 60-day scenarios, not confirmed supplier orders. Open orders, inbound coverage, profitability and own-cash constraints remain explicit blockers. Missing inbound matches never mean no goods are on the way: incomplete coverage suppresses the order-quantity scenario. Existing import lead times and batch/line minimums are included as conditional constraints, without assuming every product is imported. Supplier terms cannot be invented.
- Before asking about cost it searches existing TRY/USD/import cost fields, notebook references and all non-cancelled previous questions. A recorded cost becomes reconciliation work; a previous answer becomes research, not another question. Truncated/unavailable notebook or catalog context prevents claiming an exhaustive cost search. New questions have stable ids, are prioritized and written once without a global open-question limit.
- Answers are stored as unverified context, with an audit entry. Merely reading an answer does not mark it financially applied or change product costs. Changes and references to attachments remain review work. Arbitrary text, SQL and commands inside notes/answers are never executed.
- Proposal revisions are hashed. Approvals re-read sources, require matching revision and a recent observation, and have recorded actor/time. Materially changed approved proposals require new review. A disappearing signal does not count as successful implementation. Rejection and completion require a reason/result. Rejected items stay rejected unless the risk escalates to a higher priority; routine day-to-day changes do not repeatedly ask for the same decision. Event routes have explicit duration budgets for after-response evaluation. Approval records acceptance of a proposal; it does not trigger payments, supplier orders, marketplace edits, new loans or financial balance changes.
- Goals use the existing configured monthly USD target and dated settings exchange rate. Incomplete revenue yields unknown target progress; unknown contribution profit remains null. Total recorded debt is read from the existing cfo_servet.borc source; if unavailable it stays null. Card debt is explicitly not a substitute for total company debt. Goal observation changes are preserved in the audit trail, without being presented as verified realized gains. Reported outcomes are user statements, not automatically verified realized gains.

## Operating checks and remaining scope

The success heartbeat is written only after the durable cycle commits. Failures record a fixed diagnostic without raw SQL, credentials or financial text. UI displays last success/failure and never equates deployment with a successful live business run. The coding environment has no production credential/session, so authenticated execution is confirmed through the application UI or the next scheduled cron, not by bypassing auth.

This release is an autonomous deterministic internal research/decision workflow. It is not a general-purpose LLM employee, external market researcher or a reliable prediction of future profit. It cannot complete unverified supplier research merely by repeating a template. Provider-based reasoning, verified procurement plans and automatic execution need additional independently tested capabilities. Existing release/financial acceptance flags and frozen comparisons remain unchanged.

Validation uses synthetic PGlite tables: real persistence and stable ids, repeat runs, answer/note matching, SKU collisions, null financial outputs, explicit product policy, approval expiry/revision changes, result guards and audit records. Typecheck, lint, build and unauthenticated page/API/cron gates are part of CI.

Technical delta lives here and CHANGELOG-CFO-WORKFLOW.md. The existing large PDKS/CHANGELOG documents previously rejected by automatic privacy review are not republished.

## Question attachments

Automatic review caught the legacy action storing public attachment URLs. The working-loop integration now uploads only after verifying the existing cfo-files bucket is private. It stores a private object reference and serves downloads through ADMIN/CFO_READ/EXECUTIVE_READ authentication with attachment disposition and no-store headers. An unavailable/public bucket blocks uploads; answer text remains saved. It does not create buckets, change storage permissions or publish files. Legacy references are confined to the configured project and bucket; the application no longer links directly to them. Existing exposure through a legacy public bucket is not claimed repaired by a code deployment. Synthetic tests reject public storage, arbitrary URL hosts and path traversal.
